## The problem

On the instrumented run, transactions showed 21% change. The alert fired correctly and nobody could act on it, which is its own kind of failure. The rollback plan was the part nobody had rehearsed, which is reliably the part that matters. An average hid a tail that was doing all the damage.
## The design

I no longer trust a health check that only proves the process is running. My recorded figure for transactions is 14% change. We now write down what we expect to see before deploying, which catches surprises early. We spent longer agreeing what done meant for the timeout budget than on the implementation itself.
## Implementation notes

That gave transactions of 26% change, which I wrote down at the time. Documenting the failure mode turned out more valuable than documenting the happy path. Nobody had rehearsed the rollback, so we rehearsed it afterwards and wrote it down.

Adding a metric to the queue consumer before adding a fix is the only reason we caught the regression at all.

## What I measured

The fix was four lines; the diagnosis took two days. We added one metric, waited a week, and the cause became embarrassingly clear. Retries around the cache layer made the symptom disappear and the underlying problem considerably worse.

Because the consumer fell behind quietly, the first symptom was a customer report.

## The lesson

Small boring changes with a measurement attached beat clever changes without one, every time. Because a timeout longer than the caller's is not a timeout but a leak, we shortened it deliberately.
