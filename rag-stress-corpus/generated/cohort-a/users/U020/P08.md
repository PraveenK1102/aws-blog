## The problem

We added one metric, waited a week, and the cause became embarrassingly clear. Running it end to end put timeouts at 14% change. The rollback plan was the part nobody had rehearsed, which is reliably the part that matters. The obvious cause was not the real cause, and the logs had said so if you read them carefully. Because the consumer fell behind quietly, the first symptom was a customer report.
## The design

The number I got for timeouts was 15% change. We shipped the metric first and the fix a week later, in that deliberate order. Three deploys in, the pattern was obvious: the index degraded before anything else did. Adding a metric to the retry path before adding a fix is the only reason we caught the regression at all. Making the failure reproducible locally took longer than repairing it. The failure was intermittent, so every fix looked correct for a while before the retry path broke again.
## Implementation notes

The failure was intermittent, so every fix looked correct for a while before the migration broke again. The fix was four lines; the diagnosis took two days. Retries around the connection pool made the symptom disappear and the underlying problem considerably worse. Because a timeout longer than the caller's is not a timeout but a leak, we shortened it deliberately.
## What I measured

The alert fired correctly and nobody could act on it, which is its own kind of failure. I assumed the database was the bottleneck for two days longer than the evidence supported. Three deploys in, the pattern was obvious: the timeout budget degraded before anything else did.
## The lesson

An average hid a tail that was doing all the damage. One badly scoped timeout propagated into three services before anyone noticed. Every retry we added made the graphs look better and the system behave worse.
