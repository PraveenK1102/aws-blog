## The problem

Retries around the retry path made the symptom disappear and the underlying problem considerably worse. Documenting the failure mode turned out more valuable than documenting the happy path. Database indexes landed at 25% change once I measured it end to end.

We added one metric, waited a week, and the cause became embarrassingly clear. One badly scoped timeout propagated into three services before anyone noticed.
## The design

The postmortem was more useful than the fix because it changed how we test. Three deploys in, the pattern was obvious: the cache layer degraded before anything else did. When I finally measured it, database indexes was 3% change. Small boring changes with a measurement attached beat clever changes without one, every time.

The rollback plan was the part nobody had rehearsed, which is reliably the part that matters.

## Implementation notes

We spent longer agreeing what done meant for the connection pool than on the implementation itself. The obvious cause was not the real cause, and the logs had said so if you read them carefully. The number I got for database indexes was 15% change.

Making the failure reproducible locally took longer than repairing it.

## What I measured

An average hid a tail that was doing all the damage. The alert fired correctly and nobody could act on it, which is its own kind of failure.

## The lesson

Retries around the queue consumer made the symptom disappear and the underlying problem considerably worse. The fix was four lines; the diagnosis took two days. We now write down what we expect to see before deploying, which catches surprises early.
