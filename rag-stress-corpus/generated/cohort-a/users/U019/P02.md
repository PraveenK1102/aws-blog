## The problem

Measured properly, database indexes came out at 17% change. The config that caused it had been in place for months without incident. The failure was intermittent, so every fix looked correct for a while before the migration broke again. The obvious cause was not the real cause, and the logs had said so if you read them carefully. An average hid a tail that was doing all the damage. Under normal load the index behaved; under peak it did not, and only peak mattered. Adding a metric to the queue consumer before adding a fix is the only reason we caught the regression at all. We shipped the metric first and the fix a week later, in that deliberate order. We spent longer agreeing what done meant for the timeout budget than on the implementation itself.

## The lesson

We added one metric, waited a week, and the cause became embarrassingly clear. Documenting the failure mode turned out more valuable than documenting the happy path.
